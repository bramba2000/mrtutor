# Backend CRUD feature

Scaffolds one feature-first vertical slice — `backend/features/<name>/`, `<name>sqlite/`, `<name>http/` — following the exact shape of the `auth` and `students` features. Templates for every layer live in `references/`; this file is the process: gather the spec, reconcile it against anything already on disk, generate each layer, then wire it in.

Go backend only (`backend/`). Not for frontend work.

## Vocabulary

- **Feature** — the plural lowercase package name and directory, one token, no underscore (`students`, `lessonplans`). Becomes the table name (snake_case plural) and the URL prefix.
- **Entity** — the singular PascalCase Go type (`Student`, `LessonPlan`).
- **Base ops** — `GetByID`, `GetAll`, `Save` (upsert: zero ID inserts, non-zero ID updates-or-creates-at-that-id), `Delete`. Every feature has these regardless of what the user asked for.
- **Extra ops** — anything beyond base ops the user named (`GetByEmail`, `ListByClass`, `Archive`, a bulk import...). Each is a read or a write; treat it as a vertical addition to every layer, not a special case.

## Step 1 — Pin down the spec

Before writing anything, you need: the feature name, the entity's fields (name, type, required/optional, format constraint), and the full list of extra ops with their inputs/outputs. If the user's request already states these, proceed — do not ask for confirmation of what was already said. If a field's type, optionality, or an extra op's shape is genuinely missing or ambiguous, ask for exactly that (a direct question or `AskUserQuestion`); never invent a business field or silently drop a requested operation.

**Done when:** you can name every file from Step 3 and state every field and op it must contain, with no placeholder left to guess at.

## Step 2 — Reconcile with what's already there

The user may have hand-written part of this feature already, committed or not. Find it before generating anything:

```
git status --porcelain -- backend/features/<name> backend/sqlite/migrations backend/sqlc.yml backend/test/integration
find backend/features/<name> -type f 2>/dev/null
```

Read every file that already exists at any layer (domain, service, queries.sql, sqlite repository, http handlers, migration, the feature's `sqlc.yml` block, tests). Its field names, types, error kinds, and method signatures are authoritative for that layer — generate the *remaining* layers to match them, don't rewrite what's already there to match a different shape.

**Conflict:** if the spec from Step 1 contradicts something already implemented — a field missing from one side, a differing type, a differing validation rule, an operation only one side has — stop generating. State the concrete contradiction (file + what it has vs. what was requested) and ask the user which side wins. Never resolve a spec-vs-code conflict by guessing, and never overwrite hand-written code to make a contradiction disappear.

**Done when:** every file found in this step is classified as reuse-as-is, needs-additions-only, or flagged-as-conflict-and-escalated — before any new file is written.

## Step 3 — Lay out the files

Exactly these, nothing else, mirroring `students`:

```
backend/sqlite/migrations/NNNN_create_<table>.sql
backend/features/<name>/domain.go
backend/features/<name>/service.go
backend/features/<name>/service_test.go
backend/features/<name>/<name>sqlite/queries.sql
backend/features/<name>/<name>sqlite/repository.go
backend/features/<name>/<name>sqlite/repository_test.go
backend/features/<name>/<name>http/handlers.go
backend/features/<name>/<name>http/handlers_test.go
backend/test/integration/<name>_test.go
```

`<name>sqlite/internal/gen/` is generated by sqlc in Step 5 — never hand-write into it. Do not create `entity/`, `usecase/`, `dto/`, or `repository/` subpackages; the domain package stays flat. Do not touch `backend/httpx/` or existing files under `backend/sqlite/` other than adding one migration — see the wiring gate in Step 7.

## Step 4 — Domain layer

Read `references/domain.md`, then write `domain.go`: the entity struct, `ErrNotFound` (and any other domain errors an extra op needs), and the `Repository` interface covering base ops plus every extra op from Step 1.

**Done when:** `domain.go` compiles standalone (it has no imports beyond `context`, `time`, `errs`) and every extra op from Step 1 has a matching interface method with a doc comment.

## Step 5 — Migration, queries, sqlc, sqlite repository

Read `references/sqlite.md`, then, in order: write the migration (next number after the highest in `backend/sqlite/migrations/`), write `queries.sql` (one query per base op plus one per extra op), add the feature's block to `backend/sqlc.yml`, run `task sqlc` (or `go tool -modfile=go.tool.mod sqlc generate` from `backend/`) to materialize `internal/gen`, then write `repository.go` implementing `Repository` against the generated `gen.Queries`.

**Done when:** `go build ./...` succeeds from `backend/` and `internal/gen` contains the generated code — sqlc ran before the repository was written, not after.

## Step 6 — Service and HTTP layers

Read `references/service.md` and write `service.go`: `Service` wrapping `Repository`, `CreateIn`/`UpdateIn` with `Validate()`, and a method per base and extra op, validating write inputs and passing reads straight through.

Read `references/http.md` and write `<name>http/handlers.go`: the consumer-side `Service` interface, `Handler`, `Mount(*httpx.Router)` registering one route per op under `/<name>`, and a decode helper per route.

**Done when:** the `<name>http.Service` interface is satisfied by `<name>.Service{}` (assert it with a blank `var _ Service = ...`), and every op from Step 1 has a route.

## Step 7 — Wire it in

Read `references/wiring.md` and make exactly these edits — the scaling gate this codebase holds every feature to is that adding one touches *only* its own directories, one migration, one `sqlc.yml` block, and these three lines:

1. `backend/sqlc.yml` — new feature block (done in Step 5).
2. `backend/cmd/api/service.go` — add the field to `Services` and the two lines in `createServices` that build the repository and service.
3. `backend/cmd/api/routes.go` — add the handler to the `handlers` slice in `registerRoutes`.

If wiring this feature requires touching anything else (`httpx/`, the `sqlite` package proper, another feature's files), stop and flag it — that means the shape has drifted from the established layout, not that the extra edit is fine to make quietly.

**Done when:** `go build ./...` succeeds and the new routes are reachable — confirmed by the tests in Step 8, not by inspection alone.

## Step 8 — Tests

Read `references/tests.md` and write all four: `service_test.go` (fake repository), `<name>sqlite/repository_test.go` (real sqlite via `sqlitetest.OpenTemp`, skipped under `-short`), `<name>http/handlers_test.go` (fake service + fake authenticator, driven through the real router), and `test/integration/<name>_test.go` (real db + real router, full auth'd/unauth'd lifecycle, skipped under `-short` via `skipIfNotIntegration`). Cover every extra op the same way the base ops are covered: happy path, the domain error path, and — for writes — the validation-failure path.

**Done when:** from `backend/`, `task unit-test` (`go test -short ./...`) and `task test` (`go test ./...`) both pass, and `task vet` is clean.
